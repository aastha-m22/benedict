How the debug console is put together

Slack stays the place you talk to Benedict. This page is a local inspector: one inbound event becomes one run, and the UI shows the timed pipeline that produced the reply.

localhost:8765 Same process as the Slack bot Read-only UI

1. What this is

A thin browser console that starts with the Slack bot. Open http://127.0.0.1:8765, pick a mention or MCP call, and see route, search, context, Claude, tools, and the Slack reply.

It is not a second chat. It does not onboard repos or send Slack messages.

2. Why it exists

Before this, debugging meant tailing Rich logs and guessing which mention they belonged to. You could not answer:

  1. Why did this mention take the metadata shortcut?
  2. What did semantic search return?
  3. Which files went into Claude?
  4. What gh argv ran, and what came back?

workspace_log.json only records coarse actions (onboard, index). A run recorder was required.

3. The core idea

The primary object is a run: one Slack mention, thread reply, command, index job, or MCP tool call.

Begin

Slack or MCP starts a run and stores it in memory as running.

Stages

Handlers append timed steps: route, classify, search, context, llm, tool, reply.

Finish

The run is appended to runs.jsonl. The UI polls and shows it.

4. Architecture

The HTTP server lives in the Slack process. MCP is a separate process and writes to the same runs.jsonl when both share BENEDICT_DATA_DIR.

Slack / MCP event │ ▼ RunRecorder.begin() contextvar: current run │ ├── route ├── classify metadata shortcut, or skip ├── search Chroma hits ├── context files sent to Claude ├── llm ├── tool* run_github / metadata └── reply │ ▼ RunRecorder.finish() → $BENEDICT_DATA_DIR/runs.jsonl │ ▼ GET /api/runs GET /api/runs/{id} │ ▼ Browser http://127.0.0.1:8765
Recording must not raise into Slack. If the JSONL write fails, the mention still replies. The UI never writes.

6. Request flow

Slack mention

  1. slack_app.handle_app_mention starts a run with the cleaned query.
  2. It sets kind and route (command, conversation, architect, index).
  3. RepoAgent.handle_* runs. Conversation path may classify, search, call Claude, and execute tools.
  4. Each of those steps calls record_stage if a run is current.
  5. A finally block finishes the run with the Slack reply (or the error text).

MCP

BenedictMcpService wraps public methods. ask_benedict reuses build_context, so search and context stages appear on MCP runs too. The MCP process writes mcp.pid so the Slack-side header can show whether MCP is up.

7. A run record

{ "id": "A1B2C3D4E5F6", "source": "slack", // or "mcp" "kind": "conversation", // command | architect | index | mcp "status": "ok", // running | ok | error "duration_ms": 2340, "channel_id": "C123", "repo": "acme/backend", "query": "What files handle authentication?", "route": "handle_conversation", "reply": "*Auth lives in* `src/auth/…`", "stages": [ { "name": "route", "duration_ms": 4, "label": "conversation" }, { "name": "search", "duration_ms": 312, "detail": { "hits": [...] } }, { "name": "tool", "child": true, "label": "run_github ['pr', 'list']" } ] }

Stage names are fixed: route, classify, search, context, llm, tool, reply. Payloads over 32 KiB are truncated.

8. HTTP API

Stdlib ThreadingHTTPServer. Bind 127.0.0.1 only. No FastAPI.

PathReturns
GET /The console HTML.
GET /api/statusVersion, uptime, slack/mcp/chroma/state chips.
GET /api/runsNewest-first summaries. Filters: source, status.
GET /api/runs/{id}Full run with stages and reply.
GET /api/workspacesOnboarded channels from state.json.

The mock at OPERATOR_UI.html used fake rows. The shipped page is src/benedict/operator_ui/static/index.html and reads the API.

10. How to use it

  1. Start the bot: make run.
  2. Log line: Operator UI http://127.0.0.1:8765.
  3. Open that URL.
  4. Mention Benedict in Slack. The run appears within two seconds.

On by default. Set BENEDICT_OPERATOR_UI=0 to disable. Port: BENEDICT_OPERATOR_UI_PORT (default 8765).

Local operator only. No auth. Do not bind this to a public interface.
